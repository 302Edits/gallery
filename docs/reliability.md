# Public gallery reliability plan

Status: owner-confirmed targets; operationally provisional, not a live SLO or SLA.
There is no production deployment, metrics history, active alerting, or verified
backup/restore evidence in this review. Nothing here claims measured compliance.

## Scope and accountability

- Service: `public-sports-photo-gallery`.
- Owner: **Site owner**; responsible for publishing, backups, checking failures,
  restoring service, and reviewing these objectives. No paid on-call coverage or
  provider availability guarantee is assumed.
- Protected journey: browse published sports albums and download unchanged,
  full-quality originals on phones or computers.
- Architecture boundary: static, zero-cost public archive; computer-only owner
  management on loopback. Uploading, preparation, drafts, the local database,
  and owner credentials are outside the public request SLO and must not ship
  in the public export.
- Review monthly during initial operation, then at least quarterly; also review
  after any incident, hosting change, or major traffic/retention change.

The owner accepted the success target, cached first-byte targets, and owner
accountability. Detailed measurement, alert routing, and error-budget actions
below are implementation recommendations, not additional confirmed promises.

## Request-success SLI

target: 99.0%

window_days: 30

The window is the preceding **rolling 30 days**, not a calendar month.

**Denominator:** all eligible human public request attempts for published album
pages, their manifest/data, required application assets, previews, and original
downloads. Count retries as separate attempts; follow redirects to one final
outcome per attempt. A range download request is one attempt, not a whole album.

**Numerator:** eligible attempts with a usable successful response: HTTP 200,
correct 206 range, or 304 with a valid already-cached representation. The
expected content must be usable; an HTML error page with status 200 is not a
successful image or manifest. An original/range response must complete without
truncation. Redirects alone are not successful outcomes.

Count timeouts, network/protocol failures, 5xx, 429, broken links generated by
the site, and operator-caused 401/403/404 as bad attempts. A failed attempt does
not become good because a later retry works. Do not silently omit failures when
the success-only server log cannot see them.

Exclude known bots, synthetic probes, local owner operations, invalid URLs
typed independently of the site, deliberately denied private resources, and
explicit user cancellations/navigation aborts. Keep exclusion counts visible.
Browser memory/disk-cache hits with no outgoing request are outside this
network-request denominator, not extra successes. Bot classification and the
timeout/incomplete-transfer policy must be implemented and documented before
activating measurement; they are not verified today.

Formula: `SLI = good_eligible_attempts / all_eligible_attempts`.
Zero attempts means **no data**, never 100% success. Report request counts and
coverage alongside the ratio, with separate browse/preview/original-download
breakdowns so a high preview volume cannot hide broken downloads. These
breakdowns do not create new, independently agreed SLO targets.

**Measurement point, proposed:** browser-observed requests at the public edge,
reconciled with whatever provider request data is actually available for free.
Record only aggregate outcome, journey class, cache state, and timing; avoid
photo contents, raw EXIF, credentials, and visitor-identifying payloads. No
telemetry collector or paid monitoring service has been deployed. Edge logs
alone miss some client failures; synthetic checks are supplementary evidence,
not substitutes for the human-request denominator. Missing coverage must be
reported as unknown, not a healthy SLI.

These definitions prioritize measurable user journeys, consistent with
[Google's SLO guidance](https://sre.google/workbook/implementing-slos/).

## Cached first-byte latency targets

| Quantile | Confirmed target |
| --- | --- |
| p50 | ≤ 150 ms |
| p95 | ≤ 500 ms |
| p99 | ≤ 750 ms |

These are **targets to measure**, not measured numbers. Measure cached public
network resources separately from cold cache, local browser-cache hits, and
local owner processing. Use browser resource timing
`responseStart - requestStart` for request-to-first-byte timing, with observed
redirect overhead reported separately. Include bad-status responses that have
observable first-byte timing; no-first-byte failures remain bad requests and
are reported separately, never replaced with a fast latency value.

Proposed reproducible reference: current desktop Chromium and a 390 × 844
mobile viewport, a recorded northeastern-US test location, warm CDN cache,
≥ 20 Mbps connection and baseline RTT ≤ 50 ms. Record actual browser version,
location, network conditions, sample count, and verifiable cache status. If
cache status or timing access is unavailable, classify it as unknown rather
than asserting a cache hit. This environment is proposed, not validated or a
promise for every visitor. Test slower mobile connections separately.

Gather a full 30-day baseline after deployment. Compute quantiles from raw
observations (not averages of daily percentiles) and disclose sample counts;
a small sample cannot substantiate p99. Until then publish no compliance claim.
The latency goals do not establish an independently agreed latency error
budget or imply 99% of full photo downloads complete in 750 ms.

**Full 20 MB transfer completion is separate and network-dependent.** Report
download completion time, bytes, cancellation/error rate, and device/network
conditions independently. Verify original and ZIP-extracted bytes against
their recorded SHA-256 in tests and restore drills, without extra duplicate
original fetches for routine monitoring. Cached TTFB alone does not prove a
smooth gallery or original-byte correctness.

## Error budget policy

At the agreed target, the budget is **1% of eligible request attempts** in the
rolling window: `allowed_bad = 0.01 × eligible_attempts`. Compliance requires
`bad_attempts / eligible_attempts ≤ 0.01`. When counts are known, remaining
fraction is `1 - bad_attempts / allowed_bad`; zero traffic is undefined.

The skill calculator also prints 432 minutes / 7.2 hours for a 30-day 99%
time-availability objective. **That is not this request-based budget and is not
an approved downtime allowance.** Do not translate failed requests into outage
minutes: traffic is uneven, especially around gallery launches.

Recommended owner actions, once trustworthy measurement exists:

| State | Remaining request budget | Owner action |
| --- | --- | --- |
| Healthy | > 50% | Publish normally after export and smoke-test checks. |
| Caution | > 25% and ≤ 50% | Review risky changes; keep a verified rollback export. |
| Critical | > 0% and ≤ 25% | Pause risky new publishing/features; prioritize repair or rollback. |
| Exhausted/violated | ≤ 0% | Restore the last verified public version; investigate and record the cause. |
| Unknown | Missing or insufficient coverage | Make no health claim; establish data and inspect reported failures. |

Security fixes and incident recovery may proceed during a freeze with the
owner's documented decision. After restoration, record corrective actions and
reassess the target against actual data. No automatic freezes or rollbacks are
currently installed.

### Proposed multi-window checks, not deployed alerts

Define `burn_rate(window) = observed_bad_fraction(window) / 0.01`. Both windows
in a row must exceed the listed threshold. These are the provided calculator's
outputs for 99% over 30 days:

| Check | Long / short window | Burn rate | Bad fraction in both windows | Proposed response |
| --- | --- | --- | --- | --- |
| Fast | 1 h / 5 min | > 14.4× | > 14.4% | Urgent owner investigation |
| Sustained | 6 h / 30 min | > 6× | > 6% | Owner investigation |
| Trend | 3 d / 6 h | > 1× | > 1% | Owner follow-up item |

The tool labels the first two checks `page`; this archive has no configured
pager, notification channel, or 24/7 response commitment. Implement neither
paid alerting nor automatic notifications without choosing an actual route.
Avoid alerts based on tiny denominators: validate minimum-count settings using
real launch and quiet-period traffic; those settings are not fixed here. During
quiet periods, small synthetic browse/manifest checks can reveal problems but
must stay separate from real-user SLO accounting. Never poll every full-quality
original for monitoring. Multi-window and low-traffic considerations follow
[Google's alerting guidance](https://sre.google/workbook/alerting-on-slos/).

## Backup and recovery objectives

| Data/service | Objective | Condition and evidence required |
| --- | --- | --- |
| Original photos | RPO: zero original loss | Independent copies exist and every retained original's size/hash is verified. This is conditional, not established durability. |
| Published gallery metadata | Restore latest verified post-publication snapshot | Snapshot includes album settings, photo mappings, dates/sport/location, and original hashes; validate after each publication. |
| Draft metadata | Proposed RPO ≤ 24 h | Daily snapshots are a recommendation, **not independently confirmed**; no verified cadence exists. |
| Public service | Best-effort RTO ≤ 24 h | Measure from service interruption to verified restoration; owner availability, transfer time, and provider outages can prevent this target. |

Independent means a separate failure domain, not just the public host or another
folder on the same disk. Keep original bytes unchanged; generated previews can
be recreated. A public static export is not by itself a private-owner database
backup and must not contain drafts or credentials. No original retention or
album-expiry policy was authorized. Zero-cost hosting does not provide free,
unlimited independent backup capacity or guarantee restoration in 24 hours.

Proposed recovery drill before launch, then periodically and after storage
changes:

1. Obtain the independent originals and latest verified metadata snapshot.
   Open/recover the private manager backup in an isolated local environment.
2. Check original inventory, sizes, and SHA-256; report missing/corrupt copies
   rather than asserting RPO zero. Confirm the last published album membership.
3. Regenerate previews and rebuild a published-only static export. Re-run file
   size/count preflight checks; do not shrink originals or expire albums to fit.
4. Restore the last verified public export through the chosen free hosting path
   when available. Preserve recovery copies and do not overwrite good backups.
5. Verify mobile/desktop browsing and individual/batch original downloads,
   including ZIP extraction/hash equality. Record interruption/restoration
   times, backup dates, missing data, and measured RPO/RTO.

Recovery objectives are distinct from request reliability, as described in
[AWS recovery-objective guidance](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_planning_for_recovery_objective_defined_recovery.html).
No restore drill or independent-copy verification has yet been performed.

## Tool validation and activation gate

The provided `slo_designer.py` rendered this service's request-success design
with explicit owner, numerator/denominator, 99% target, rolling 30-day window,
and a reference to this policy. `error_budget_calculator.py` produced the
thresholds above. Their successful execution validates input completeness and
arithmetic, **not deployed reliability**.

Run `slo_review.py --slo-doc docs/reliability.md`. Its `target_too_low` warning
for target ≤ 99% is expected and retained: the owner explicitly accepted 99%
as the low-cost starting point. The review is **not a clean pass**. Inspect
actual results in `slo-review.json`; no warning is suppressed or target raised
without owner agreement. Review again after the first measured rolling window.

Before calling this SLO live: deploy the public site, validate real/free
measurement coverage, collect a 30-day baseline, verify independent backups and
a restore drill, finalize the measurement/exclusion/timeout definitions and
owner response procedure, and explicitly disposition the review warning. None
of those activation checks is claimed complete by this document.
